# 基础设施部署手册：镜像拉取 + 镜像构建（手动执行版）

> 本手册给出**手动拉取 / 手动构建**的完整命令清单。所有镜像名与版本均为 **2026-09-04 实测确认**，可直接逐条复制执行。

## 一、先看结论：一共 4 个镜像 + 1 个自建

| # | 组件 | 镜像名 | 来源 | 用途 | 端口 | 约大小 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | etcd | `quay.io/coreos/etcd:v3.5.5` | quay.io 直连 | Milvus 元数据存储 | 2379（内网） | ~35 MB |
| 2 | MinIO | `minio/minio:RELEASE.2023-12-20T01-00-02Z` | Docker Hub 官方 | Milvus 对象存储 | 9000 / 9001 | ~150 MB |
| 3 | Milvus | `milvusdb/milvus:v2.5.27` | Docker Hub 官方 | 向量库（dense+sparse 混合检索） | 19530 / 9091 | ~1.4 GB |
| 4 | Attu（可选） | `zilliz/attu:v2.5` | Docker Hub 官方 | Milvus 可视化管理界面 | 3000 | ~600 MB |
| 5 | BGE-M3 | `kb-bge-m3:latest` | **本机自建**（含烘焙权重） | 向量化服务（dense 1024 维 + sparse） | 8003 | 构建产物 ~11 GB |

> #5 不是拉取，是从 `deploy/embed/Dockerfile` 构建。其余 4 个直接 `docker pull`。

### 版本选型说明（2026-09-04 核实）

- **Milvus 用 `v2.5.27`**：v2.5 LTS 系列最新 patch。与 `v2.5.4` 功能完全一致（`SPARSE_FLOAT_VECTOR` + sparse 索引 + hybrid_search + RRF 融合都原生支持），但补上了 23 个 patch 的稳定性改进和 2 个 critical CVE 修复（v2.5.21、v2.5.27）。
- **不上 v2.6**：v2.6 主打 BM25 加速、分层存储、Woodpecker 去消息队列，均面向大规模集群场景；本项目单机万级文档、走 BGE-M3 learned sparse，收益为 0，却要连带升级 MinIO（Woodpecker 要求 ≥2024-12-18）和 etcd，得不偿失。
- **MinIO 用 `RELEASE.2023-12-20`、etcd 锁 `v3.5.5`**：Milvus v2.5 系列用 RocksMQ，无 Woodpecker 条件写入依赖，MinIO 只要 ≥ Milvus 官方安全基线 `RELEASE.2023-03-20` 即可（v2.2.5 起为修旧版 CVE 才升到该版本）。选 `2023-12-20` 比官方基线多 9 个月 bug 修复，S3 接口完全兼容；注意环境变量须用新名 `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`（旧的 `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` 自 2021-04 起已弃用，随时可能被移除）。

## 二、镜像拉取（手动逐条 / 一条龙）

### 逐条执行

```bash
# 1. etcd（quay.io 独立 registry，无需任何前缀）
docker pull quay.io/coreos/etcd:v3.5.5

# 2. MinIO
docker pull minio/minio:RELEASE.2023-12-20T01-00-02Z

# 3. Milvus（最大，约 1.4 GB）
docker pull milvusdb/milvus:v2.5.27

# 4. Attu（可选，不需要可视化管理界面可跳过）
docker pull zilliz/attu:v2.5
```

### 一条龙脚本

```bash
docker pull quay.io/coreos/etcd:v3.5.5 && \
docker pull minio/minio:RELEASE.2023-12-20T01-00-02Z && \
docker pull milvusdb/milvus:v2.5.27 && \
docker pull zilliz/attu:v2.5
```

### 拉取完成后核对

```bash
docker images | grep -E "etcd|minio|milvus|attu"
```

应看到 4 行记录。

## 三、构造新镜像：BGE-M3 向量化服务

### 3.1 为什么要自建

主流推理服务器（TEI、vLLM、Infinity、Xinference）的 `/v1/embeddings` **都只返回 dense 向量**，Infinity 官方明确标注 `bge-m3 no sparse`。而我们的混合检索依赖 BGE-M3 的 **dense + sparse 双输出**。唯一稳妥方案是用 `FlagEmbedding` 的 `BGEM3FlagModel` 自建服务。

### 3.2 构建命令

```bash
cd deploy/embed
docker build -t kb-bge-m3:latest .
```

可用构建参数（均有默认值，正常情况无需指定）：

| 参数 | 默认值 | 作用 |
| :--- | :--- | :--- |
| `APT_MIRROR` | `mirrors.aliyun.com` | Ubuntu apt 源，影响第 ② 步装 Python |
| `APT_RETRIES` | `5` | apt 下载失败重试次数 |
| `HF_ENDPOINT` | `https://hf-mirror.com` | HuggingFace 权重源，影响第 ⑥ 步烘焙权重 |
| `PIP_INDEX` | 清华 PyPI | pip 源，影响第 ③④ 步 |

> apt 源默认走国内镜像而非 archive.ubuntu.com，原因见「十、构建故障排查」。
> 若你的网络直连官方源正常，可显式指定：`--build-arg APT_MIRROR=archive.ubuntu.com`

### 3.3 构建过程会发生什么

| 步骤 | 内容 | 说明 |
| :--- | :--- | :--- |
| ① 拉基础镜像 | `nvidia/cuda:12.4.0-runtime-ubuntu22.04` | 约 1.6 GB |
| ② 装 Python | `apt-get install python3.10 python3-pip` | 走 `APT_MIRROR` 指定的 apt 源 |
| ③ 装 PyTorch | `pip install torch==2.6.0`（cu124） | **最大单包**，约 2.7 GB，走清华源，失败自动回退官方 PyPI |
| ④ 装依赖 | `fastapi / uvicorn / FlagEmbedding==1.3.3 / huggingface_hub / numpy` | — |
| ⑤ 拷入代码 | `COPY server.py` | 向量化服务本体 |
| ⑥ 烘焙权重 | `snapshot_download('BAAI/bge-m3')` → `/models/hub/` | **构建期下载 ~2.2 GB**，目标机无需联网 |

### 3.4 关键：模型权重在「构建期」就烘焙进镜像

为了让**目标机（内网生产服务器）完全离线部署**，Dockerfile 在构建阶段就调用 `huggingface_hub.snapshot_download` 把 `BAAI/bge-m3` 完整权重下载到 `/models/hub/` 并打入镜像层。容器启动时 `BGEM3FlagModel` 会自动从这个标准 HF 缓存路径加载权重，**无需任何现场下载**。

构建机要求：能联网（首次构建时从 `hf-mirror.com` 下 ~2.2 GB）。可通过 `--build-arg HF_ENDPOINT=...` 切换镜像源，例如：
```bash
docker build --build-arg HF_ENDPOINT=https://hf-mirror.com -t kb-bge-m3:latest ./embed
# 或走官方：
docker build --build-arg HF_ENDPOINT=https://huggingface.co -t kb-bge-m3:latest ./embed
```

目标机要求：**完全离线可用**。`docker load -i kb-bge-m3.tar` 之后就开箱即用，零额外配置。

### 3.5 构建产物大小

`kb-bge-m3:latest` 约 **11 GB**（CUDA runtime ~1.6 GB + PyTorch ~2.7 GB + 依赖 + BGE-M3 权重 ~2.2 GB + 中间层）。构建机需预留约 **15 GB** 临时空间。

## 四、启动全套（镜像已就位后）

```bash
cd deploy
docker-compose up -d
```

此时所有镜像已手动 pull / build 完成，compose 不会再触发拉取。

```bash
# 查看状态
docker-compose ps
# 观察 Milvus 启动日志（首次约 30~60 秒就绪）
docker-compose logs -f milvus
# 观察 BGE-M3 加载进度（权重已烘焙，只需等 CUDA 初始化）
docker-compose logs -f bge-m3
```

（可选）启动可视化管理界面：

```bash
docker-compose --profile tools up -d attu
# 浏览器访问 http://localhost:3000
```

> **命令形式**：本机只提供 `docker-compose`（带连字符）v5.4.0，**没有** `docker compose`
> （V2 插件形式）。跑 `docker compose up -d` 会报 `docker: unknown command: docker compose`。
> 本文档统一用 `docker-compose`。

### 4.1 数据卷存在哪里

compose 文件末尾声明了三个 **named volume**：

| compose 里的名字 | 实际卷名 | 容器内挂载点 | 存的内容 |
| :--- | :--- | :--- | :--- |
| `etcd-data` | `deploy_etcd-data` | `/etcd` | Milvus 元数据（collection schema 等） |
| `minio-data` | `deploy_minio-data` | `/minio_data` | **向量与索引数据的主体**（Milvus 当 S3 用） |
| `milvus-data` | `deploy_milvus-data` | `/var/lib/milvus` | Milvus 本地文件（WAL、日志等） |

**卷名带项目前缀**：compose 会自动加前缀，项目名默认取 compose 文件所在目录名，
当前是 `deploy/`，所以实际卷名是 `deploy_etcd-data` 这种形式，**不是**裸的 `etcd-data`。
想确认可运行 `docker-compose config` 看 `volumes:` 段。

**物理位置**（`docker volume inspect` 实测的 Mountpoint）：

```
/var/lib/docker/volumes/deploy_etcd-data/_data
/var/lib/docker/volumes/deploy_minio-data/_data
/var/lib/docker/volumes/deploy_milvus-data/_data
```

这是 **WSL2 Linux 虚拟机内部**的路径，不是 Windows 的普通目录。查真实路径用：

```bash
docker volume inspect deploy_milvus-data --format "{{.Mountpoint}}"
```

想从 Windows 资源管理器浏览，地址栏输入（Docker Desktop WSL2 后端）：

```
\\wsl.localhost\docker-desktop-data\version-pack-data\community\docker\volumes
```

> ⚠️ **不要直接编辑这些文件**。卷里是 etcd 的 BoltDB 和 MinIO 的对象存储格式，
> 手工改动极易损坏数据。要备份请用下面的打包命令，不要直接复制目录。

**备份**（PowerShell 下执行，会在当前目录生成压缩包）：

```bash
docker run --rm -v deploy_milvus-data:/data -v "${PWD}:/backup" alpine tar czf /backup/milvus-data.tar.gz -C /data .
```

**删除**：

```bash
docker-compose down      # 停止，保留卷（数据还在）
docker-compose down -v   # 停止并删除卷（向量库清空，慎用）
```

## 六、若目标机器无法访问外网（离线传输）

如果最终在**无外网的内网 Linux 服务器**部署，先在能联网的机器上构建并导出镜像，再拷过去导入：

```bash
# 1. 在联网机器上构建镜像（这一步需要联网下载权重 ~2.2 GB）
cd deploy/embed
docker build --build-arg HF_ENDPOINT=https://hf-mirror.com -t kb-bge-m3:latest .

# 2. 把全套镜像导出（生成 kb-images.tar，约 3.5 GB，Milvus + BGE-M3 是大头）
cd ..
docker save quay.io/coreos/etcd:v3.5.5 \
  minio/minio:RELEASE.2023-12-20T01-00-02Z \
  milvusdb/milvus:v2.5.27 \
  kb-bge-m3:latest \
  -o kb-images.tar

# 3. 把 kb-images.tar 拷到内网服务器

# 4. 在无外网服务器上导入
docker load -i kb-images.tar

# 5. 启动（无需联网）
cd deploy
docker-compose up -d
```

> **BGE-M3 权重已烘焙进镜像本身**（见 3.4 节），所以整个流程中权重**不作为独立卷单独导出**，内网服务器只要 `docker load` 就拥有完整权重，零现场下载。

## 七、与本机 GPU 的约束（RTX 3060 6GB）

- BGE-M3 模型约 **1.2 GB 显存**，`USE_FP16=true` 下 6GB 显存充足。
- 向量化速度预期 **300~400 条/秒**，20 万 chunk 入库约 10 分钟。
- 6GB 显存**不要**同机再跑大语言模型（Qwen3-27B 需 20G+）。LLM 走内网服务器 `192.168.124.221:8000`，这本来就符合架构。

## 十、构建故障排查

### 10.1 `apt-get update` 报 `File has unexpected size ... Mirror sync in progress?`

**现象**：构建停在第 ② 步，报类似

```text
E: Failed to fetch http://archive.ubuntu.com/ubuntu/dists/jammy-updates/main/binary-amd64/Packages.gz
   File has unexpected size (4622604 != 4622598). Mirror sync in progress?
```

**根因**：archive.ubuntu.com 主站自身正处于镜像同步的半途，`Release` 索引里登记的
`Packages.gz` 大小与实际下发的文件对不上，apt 哈希校验失败后直接 exit 100。
**这是主站侧的瞬时状态，与本机配置无关，单纯重跑也可能继续中招。**

2026-09-04 同一时刻实测对比：

| 源 | Release 登记大小 | 实际下发大小 | 是否自洽 |
| :--- | :--- | :--- | :--- |
| `archive.ubuntu.com` | 4622598 | 4622604 | ❌ 主站同步中 |
| `mirrors.aliyun.com` | 4622604 | 4622604 | ✅ |
| `mirrors.tuna.tsinghua.edu.cn` | 4622604 | 4622604 | ✅ |

国内镜像已完成同一轮同步且自校验一致（比主站还新 6 字节），所以**换源是真正的解法，
不是碰运气重试**。

**处理**：Dockerfile 已默认把 apt 源切到 `mirrors.aliyun.com`（由 `ARG APT_MIRROR`
控制），并加了 `Acquire::Retries=5` 兜底。正常构建无需任何干预。

想换其他源可显式指定（四个源实测均可达且自校验一致，4.6 MB 索引约 0.7~1.2 s 下完）：

```bash
docker build --build-arg APT_MIRROR=mirrors.tuna.tsinghua.edu.cn -t kb-bge-m3:latest .
docker build --build-arg APT_MIRROR=mirrors.ustc.edu.cn          -t kb-bge-m3:latest .
docker build --build-arg APT_MIRROR=mirrors.cloud.tencent.com    -t kb-bge-m3:latest .
```

> 换源只改写 `archive.ubuntu.com` / `security.ubuntu.com` 两个域名，
> CUDA 官方源 `developer.download.nvidia.com` 保持原样，不受影响。

### 10.2 `dockerfile parse error: FROM requires either one or three arguments`

**根因**：Dockerfile 解析器对指令关键字**大小写不敏感**。原写法用
`RUN python3 -c "..."` 写多行 Python，第二行开头的
`from huggingface_hub import snapshot_download` 里的 `from` 被当成 `FROM` 指令，
参数个数对不上（FROM 只接受 1 或 3 个）于是报解析错。

**处理**：已把权重下载逻辑抽成独立脚本 `deploy/embed/download_weights.py`，
Dockerfile 改为 `COPY` 进来再 `RUN python3 /app/download_weights.py`。

> **规则**：Dockerfile 里写多行 Python 一律单独成文件 + `COPY`，不要用跨行的
> `RUN python3 -c "..."`。行内单行写法（如 HEALTHCHECK 里那句）因为没有换行，是安全的。
