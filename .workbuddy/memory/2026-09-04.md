## Dockerfile 烘焙权重踩坑：从坑到修

**问题**：原 `deploy/embed/Dockerfile` 用 `RUN python3 -c "..."` 多行写法烘焙 BGE-M3 权重，构建时报
`dockerfile parse error on line 53: FROM requires either one or three arguments`。

**根因**：Dockerfile 解析器对指令关键字**大小写不敏感**。`RUN python3 -c "..."` 第二行开头的
小写 `from huggingface_hub import ...` 被当成 `FROM` 指令，参数数量对不上（FROM 只接受 1 或 3 个），
所以报错。`RUN` / `CMD` / `COPY` 等所有指令关键字都有此特性。

**修复**：把下载逻辑拆成独立脚本 `deploy/embed/download_weights.py`（读 ENV 变量 → snapshot_download），
Dockerfile 用 `COPY download_weights.py /app/` + `RUN python3 /app/download_weights.py` 调起。
**绝对规则**：Dockerfile 里写多行 Python 代码一律单独成文件 + COPY，禁止用 `RUN python3 -c "..."`
跨行写法（行内单行可以，比如 HEALTHCHECK 里的 `python3 -c "import urllib..."` 因为不换行所以安全）。

## apt 源踩坑：archive.ubuntu.com 镜像同步导致构建失败

**现象**：构建 kb-bge-m3 卡在第 2/9 步 `apt-get update`，报
`File has unexpected size (4622604 != 4622598). Mirror sync in progress?`，exit 100。

**根因**：archive.ubuntu.com 主站自身在同步半途——Release 索引登记的 Packages.gz 大小
与实际下发文件不一致，apt 哈希校验失败。**主站侧瞬时状态，与本机无关，重跑也可能继续中招。**

**诊断手法（可复用）**：对比「Release 登记的大小」与「实际 Content-Length」是否自洽，
就能判断换源是否真的有用，而不是盲试：
```
curl -s <mirror>/ubuntu/dists/jammy-updates/Release | grep "main/binary-amd64/Packages.gz"
curl -sIL <mirror>/.../main/binary-amd64/Packages.gz | grep -i content-length
```
2026-09-04 实测：archive.ubuntu.com 登记 4622598 / 实际 4622604（**不自洽**）；
aliyun、清华均为 4622604 / 4622604（**自洽，比主站新 6 字节**）。
阿里/清华/腾讯云/中科大四源均可达，4.6MB 索引 0.7~1.2s 下完。

**修复**：Dockerfile 加 `ARG APT_MIRROR=mirrors.aliyun.com` + `ARG APT_RETRIES=5`，
sed 改写源（兼容经典 sources.list 与 deb822 的 ubuntu.sources，**只改 archive/security.ubuntu.com，
CUDA 源 developer.download.nvidia.com 不动**），update/install 都带 `Acquire::Retries`。

**已验证**：最小复现（只跑 apt 装 python3.10）构建成功，Python 3.10.12 + pip 22.0.2 正常。

**环境小坑**：沙箱会删掉 curl 下载到 /tmp 的文件，`stat` 恒为 0。
测下载大小唯一可靠办法是管道计数：`timeout 15 curl -s URL | wc -c`
（`-w "%{size_download}"` 和 `stat` 落盘文件在沙箱里都恒为 0，两个都不可信）。

## bind mount 到 Windows 目录：能用但慢 45 倍（重要结论）

用户问「能否把卷挂到 Windows 指定目录」。**技术上可以，但强烈不建议用于数据库。**

实测（容器内连续写 200 个小文件，同一 workload）：

| 存储方式 | 耗时 | 相对 |
| :--- | :--- | :--- |
| bind mount 到 E: 盘（经 9P 协议） | **638 ms** | 45× |
| Docker named volume（WSL2 原生 ext4） | **14 ms** | 1× |
| WSL2 原生路径（非 /mnt） | 17 ms | 1.2× |

**结论：Windows 可见 = 走 9P 协议 = 慢 45 倍。** 这是 Docker Desktop WSL2 后端的固有限制，
不是配置能绕过的。etcd 对 fsync 延迟极敏感（高延迟会触发选举超时），
Milvus/MinIO 也大量随机 I/O，**挂到 Windows 盘会严重拖垮稳定性与吞吐**。

**已验证的其他事实**：
- E: 盘 bind mount 实测可用（未在 Docker Desktop 里显式配置共享也能写通）
- 挂载点权限 `drwxrwxrwx root:root`，**无属主/权限障碍**，Milvus/etcd/MinIO 可直接写
- 路径写法（compose 里两种都行）：`E:/docker-data/kb/etcd:/etcd` 或 `/e/docker-data/kb/etcd:/etcd`

**推荐**：数据库三件套**保持 named volume 不变**；需要 Windows 侧取数据就用容器打包备份，
不要为了"方便浏览"牺牲 45 倍 I/O 性能。

**✅ 用户拍板决策：保持现状**，三个卷继续用 named volume，不改 bind mount。
已校验 `deploy/docker-compose.yml`：语法有效、无 bind mount、卷名 `deploy_*` 前缀正常。
后续若要改，折中方案是只把 `milvus-data`（WAL/日志）挂到 Windows 方便排查，
`etcd-data` 和 `minio-data` 留在 named volume 保性能。

## 重启 Docker 后自动拉起：已加 restart 策略

用户问「重启 Docker 后服务会不会跟着启动」。**原配置不会**——compose 里没有任何
`restart:`，默认 `restart: no`，Docker 重启后容器停在 Exited，必须手动 `up -d`。

**已修复**：给全部 5 个服务（etcd / minio / milvus / bge-m3 / attu）加 `restart: unless-stopped`。

选 `unless-stopped` 而非 `always` 的原因：
- Docker daemon 重启 / 系统重启后自动拉起 ✅
- 容器崩溃自动重启 ✅
- 手动 `docker-compose down` 或 `docker stop` 后**不会**再自己起来 ✅（`always` 会）

**`always` vs `unless-stopped` 唯一区别就在最后一条**：`always` 连你主动停的容器也会拉起，
会和运维操作打架。长期跑的服务一律用 `unless-stopped`。

已校验：`docker-compose --profile tools config` 输出 5 处 `restart: unless-stopped`，
卷仍为 named volume 未变（attu 在 tools profile 下，不带 `--profile tools` 只显示 4 处，属正常）。

**注意**：`depends_on` 只保证启动顺序、不保证就绪。Docker 重启后 Milvus 可能比 etcd/minio
先尝试连接而短暂 unhealthy，它有 healthcheck 会自行重试，等 1-2 分钟即可，不是故障。

**Docker 构建缓存经验（可复用）**：
- Dockerfile 里所有 `COPY` 文件的改动只触发"该层 + 之后所有层"重跑，但**前面的所有层一律命中缓存**
- 所以大模型/大依赖镜像里改 Python 代码，`docker build` 是秒级而不是十几分钟
- 验证方式：build 后看镜像 ID 是否变了——变了就是真重建
- 临时用 `docker cp` 改容器内文件立刻生效，但镜像仍是旧版，**docker restart / 删除容器就丢**
- 因此流程是：改源文件 → `docker build` → compose `up -d`（会 Recreate）→ 验证
