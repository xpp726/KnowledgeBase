## 修入库全部失败：Milvus 集合 kb_chunks 不存在
- **现象**：用户上传一批 PDF，全部 failed。日志中 5 个文件 4 个同栈：
  `ingestion.py:173 ingest_bytes → vectorstore.py:190 delete_by_doc → MilvusClient.delete
  → code=100 Failed to get collection id: collection not found[database=default][collection=kb_chunks]`
- **根因**：全新环境清库后 kb_chunks 从未被建过；`ensure_collection()` 设计为惰性创建
  （启动时不建、入库时才建），但当前实现里**没有任何地方在入库前调它**；
  `delete_by_doc` 也没防御，导致"首次入库"在步骤 4 的清旧向量环节必失败。
  （第 5 个文件 `专项成本科技项目任务书（监控机器人）.pdf` 解析失败 0 页，与本 bug 无关，是 PDF 本身问题——扫描件/加密/损坏）
- **修法（defense in depth）**：
  1. `vectorstore.delete_by_doc` 开头 `if not self.has_collection(): return 0`，
     让清库后首次入库成为合法路径；
  2. `ingestion.ingest_bytes` 步骤 4 之前加 `await asyncio.to_thread(store.ensure_collection)`，
     使"集合存在"成为入库前置不变量（已存在则 skip，O(1) 查）。
- **测试**：新增 `tests/test_vectorstore.py` 3 个 case：①集合不存在时 delete_by_doc 返回 0 不调 Milvus
  ②集合存在时正确构造 filter ③kb_id 为空时不叠加 kb_id 子句。用 `monkeypatch` + `MagicMock`
  替身 MilvusClient，离线可跑。后端升至 **105 passed**。
- **端到端 smoke**：用真实 Milvus 跑 5 步流程（删集合→delete 返回 0→ensure 建→insert→delete 返回 1→drop）全过。
- **待办**：用户重新上传 4 个 PDF 应成功；第 5 个 PDF（专项成本任务书）需单独排查是否扫描件/加密/损坏。
- **设计教训**：惰性集合创建（确保运行时不浪费资源）+ 防御性 delete（容忍集合不存在），
  是矛盾的解。正确做法是**两道关都设**：ensure_collection 在写入前置 + delete_by_doc 容忍首次调用。
  单点防御会被多文档并发 / 重启 / 异常路径绕过。

## 修 Embedding 超时：设备监控 40 号入库 httpx.ReadTimeout
- **现象**：清库问题修复后，前 4 个 PDF 重传成功（襄阳电网 13.1s、新一代变电站 113.2s、
  国网河南电力 15.6s），但**设备监控 40 号 PDF 仍失败**：
  - 96 页 → 364 chunk（表格 352）
  - 日志无任何 "已写入 N/364" → 第一批 `embedder.embed(256 chunk)` 就 timeout
  - 异常：`httpcore.ReadTimeout → httpx.ReadTimeout`（精确 120 秒，与 `embed_timeout` 吻合）
- **根因**：`embed_max_batch=256` × ~500 字符/文本，BGE-M3 单批推理时长超过 `embed_timeout=120s`，
  客户端 timeout 吃掉整批文档，**没有任何重试机制兜底**。
- **修法（组合）**：
  1. `embed_max_batch` 256 → **64**（config 默认 + .env 显式设）
  2. `embed_timeout` 120 → **300** 秒（config 默认 + .env 显式设）
  3. `embedding._call` 加 **2 次指数退避重试**：仅重试网络类异常
     （httpx.ReadTimeout/ConnectTimeout/ConnectError），**4xx 与 dense 缺失立即抛**（参数错重试无用）
  4. `ingestion.ingest_bytes` 步骤 4 加每批 embed **耗时日志**（`embed 批次 [N-M/T] 耗时 Xs`）
- **新增配置**：`embed_max_retries=2`、`embed_retry_base_delay=2.0`，均走 pydantic-settings
  支持 .env 覆盖
- **测试**：新增 `tests/test_embedding.py` 10 个 case：①首次成功 ②ReadTimeout 后成功
  ③ConnectError/ConnectTimeout 后成功 ⑤重试全部失败抛 EmbeddingError ⑥4xx 不重试
  ⑦缺 dense 不重试 ⑧分批切分 ⑨空串占位 ⑩空入参返回空 ⑪sparse 缺则补空字典
  用 monkeypatch 替身 httpx.AsyncClient 的 __aenter__/__aexit__ 完整模拟 with 块。
  后端升至 **115 passed**（105 + 10）；前端 build 0 错误。
- **设计教训**：**客户端 timeout 不应依赖"典型值"**，必须 >>"最坏单批 × N 批串行"，
  且 batch 大小不能让"最坏单批"超过 timeout 的一半（否则任何一次抖动就吃掉整批）。
  重试必须分类：**可重试**（网络/超时/5xx）vs **不可重试**（4xx/参数错/数据格式错）。

## 数据假设偏差：PDFParser 缺 OCR 兜底导致扫描件 PDF 入库失败
- **现象**：5 个 PDF 中 4 个修完后，剩下 `专项成本科技项目任务书（监控机器人）.pdf`
  报"PDF 解析完成 tmpXXX.pdf：0 页"，是另一种失败，与前两个 bug 无关。
- **诊断**：用 pymupdf 直接打开 + 翻页查 block type，确认是**扫描件 PDF（图像型）**：
  - 19 页 × 1 张图/页（DCTDecode JPEG，1657×2332 px ≈ 200 DPI，DeviceRGB）
  - `page.get_text()` 返回空字符串（无文本层）
  - Producer `PDFlib Lite 7.0.5p3 (Win32)`——典型扫描→OCR（可选）→PDF 流水线
  - Adobe Reader 能打开是因为它直接渲染图像，但搜索/复制/索引都不行（无文本）
- **数据假设偏差**：当前 `app/services/parsers/pdf.py` 注释里写着"实测无需 OCR（全部为文字版 PDF）"
  ——早期 7 个招标 PDF 全是文字型，**没接 OCR 兜底**；遇到扫描件直接判 0 页失败。
- **决策**：接 RapidOCR（ONNX Runtime，与已装的 onnxruntime 1.29.0 复用）。
  - PaddleOCR 表格识别 SOTA 但 paddlepaddle ~1.5GB + 1-2GB VRAM；本机 RTX 3060 6GB 同时跑 BGE-M3+OCR 显存紧
  - RapidOCR 模型 ~200MB、ONNX Runtime <500MB VRAM、首次加载 5-10s、API 一行调用
  - 中文印刷体识别率 > 95%；表格识别弱是已知短板，但**本项目表格识别仍走 pymupdf4llm**（文字型 PDF）
  - 纯图像表格场景后续可单独补 PP-Structure
- **教训**：任何"实测无需 XXX"的注释都应附**反例条件**与**最后核对日期**。
  这次偏差是"小样本归纳"导致——7 个文字型 PDF 的统计被当作全局规律，遇到第一个反例就崩。

### doc_id 算法改造
- 旧：`md5(file_name)[:16]`（同 file_name 必冲突）

- 好处：跨 folder 同名文件产生**独立 doc_id**（不再触发"另一 folder 同名被覆盖"的隐性 bug）
- register_document 改造：
  - 接受 folder_id；folder_id 为空 → 自动用 kb 默认 folder
  - 同 folder 同名（无论 doc_id）→ `FileNameConflictError` 拒绝
  - 跨 folder 同名 → 允许（新 doc_id）
- 测试 `test_register_duplicated_flag` 由"幂等覆盖"改为"抛 FileNameConflictError"

### 数据模型
- `Folder` 表（folder_id, kb_id, parent_id, name, depth, is_system, created_at, updated_at）
  - 联合唯一索引 `(kb_id, parent_id, name)` —— parent_id IS NULL 视为同一组
- `Document` 加 `folder_id` FK（`ondelete=SET NULL`）+ 索引 `(folder_id, file_name)`
- `default_kb_folder_name: str = "默认文件夹"` 新增到 config

## MixedTree.total_doc_count 双计 bug（self 直挂 file）

### 用户反馈
"子文件和缩减正确，我刚刚删除了几个文件，发现文件计数没有同步更新"

截图：默认文件夹显示 **"12 个文档（直属 6）"**——总数是直属的 2 倍。

### 根因（公式不自洽）
后端 `FolderTreeNode.doc_count` = self 直挂 file 数（来自 `count_documents_by_folder`：
`SELECT folder_id, COUNT(*) GROUP BY folder_id`，**只算直属**不含子 folder）。

前端 store `buildFolderNode` 把 self 直挂 file 也塞进 children，但 **reduce 累计时又把
children 里的 file 视为 +1**——自己直挂 file 被算了 2 次（一次 direct_doc_count，一次 reduce 的 file+1）。

### 公式对比
- 旧（错）：`direct_doc_count + reduce(file+1, folder+=total_doc_count)` → 直属 N 项时 total = 2N
- 新（对）：`direct_doc_count + reduce(folder+=total_doc_count)` → total = 直属 + 子 folder 汇总

### 修法（store.ts + types/api.ts 同源两处）
```ts
folderNode.total_doc_count =
  folderNode.direct_doc_count +
  folderNode.children
    .filter((c): c is MixedFolderNode => c.node_type === 'folder')
    .reduce((sum, c) => sum + c.total_doc_count, 0)
```
`mixedTotalDocCount(node)` 工具函数（types/api.ts）也同步修，避免两处实现不一致。

### 测试
新加 `stores/__tests__/document.test.ts` "mixedTree.total_doc_count = direct + 子 folder 汇总"：
- 顶层 folder 直挂 3 + 子 folder(直挂 2) → 总 5（不是 8/6）

### 验证
- 前端 `npm test`：**60 passed**（含新增 1）
- 前端 `npm run build`：**通过**
- 后端 `pytest -q`：**154 passed**（未触动）

### 教训
- **当"集合中有对象"和"集合大小由另一字段表达"并存时**，reduce 必须先决定一个真相源。
  本例里 children 数组中 file 是 UI 真相源, 但 doc_count 是总数组大小——两者必须二选一：
  - children 只放子 folder（file 由 view 自己从 allDocs 拼）→ total = direct_doc_count 即可
  - children 同时放 file（已有 UI 设计）→ total 不能重复计 file
- **用户报"删除后没更新"，要看是 stale 缓存还是公式错**。本次是公式错，每次删除重算都得到错的总数，
  看起来"数字变但总不对"。两个症状叠加容易误判方向。
- **store 中私有 helper 与 types 文件中工具函数的实现必须保持同步**——加 store 改造时，
  记得回头看 types 文件同名的 helper。本例 `mixedTotalDocCount` 也是 bug 同一来源，只是没人用它所以没暴露。
