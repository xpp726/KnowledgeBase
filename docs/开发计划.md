## 一、目标与范围

### 1.1 项目目标

构建内网部署的企业知识库问答系统，支撑 **1000–10000 篇混合类型文档**的上传、解析、检索与流式问答，提供原文引用溯源与可视化管理后台。

### 1.2 本期范围（MVP）

- 全链路可运行：文档上传 → 解析 → 分块 → 向量化 → 混合检索 → SSE 流式问答 → 引用展示 → 日志统计
- **无需登录鉴权**，内网直接访问
- 不引入 OCR，但做成**可插拔模块**（接口预留，二期开启）
- 不引入 Rerank，但做成**可插拔模块**（二期按评测数据决定）

### 1.3 不在本期范围

用户体系与权限、扫描件 OCR、图片内容问答、移动端适配、文档版本管理。

### 1.4 关键指标（基于实测重新定义）

| 指标 | 目标值 | 依据 |
| :--- | :--- | :--- |
| 首字延迟 | **< 1.5s** | 实测 LLM 真实 TTFT 为 1.0–1.5s |
| 完整答案时长 | 10–15s（300 字） | 实测 21.3 tok/s，硬件决定，不可优化 |
| 检索延迟 | < 300ms | 待阶段 0 验证（Milvus 实例状态存疑） |
| 向量化吞吐 | ~360 chunk/s | 实测值 |
| 并发支撑 | 1–5 人 | 实测 3 路并发无劣化 |

> **⚠️ 指标修订说明**：原方案的"5 秒内响应"按"完整答案"计算在当前硬件下**不可能达成**（21.3 tok/s 硬约束）。经确认，指标修订为**首字 < 1.5s + 流式输出**，用户 1.5 秒内看到第一个字并持续滚动，主观体验优于干等 5 秒。这是主流 RAG 产品的通用做法。

### 2.2 LLM 服务实测

| 指标 | 实测值 | 影响 |
| :--- | :--- | :--- |
| 生成速度 | **21.3 tok/s**（关思考） | 300 字答案需 12–15s |
| 真实首字延迟 | **1.0–1.5s** | 流式首个内容分片到达时间 |
| 3 路并发 | 1.5–1.8s/请求，无劣化 | 1–5 人场景充足 |
| 思考模式 | **默认开启**（39 reasoning tokens） | ⚠️ 必须显式关闭，否则每题多耗 1–2s |
| Embedding 接口 | **404 不存在** | 该实例仅有 chat/completions |

**必须采用的调用参数**：

```json
{
  "model": "Qwen3.8-27B-FP8",
  "messages": [...],
  "stream": true,
  "max_tokens": 1024,
  "chat_template_kwargs": { "enable_thinking": false }
}
```

### 2.3 Embedding 服务实测

| 指标 | 实测值 |
| :--- | :--- |
| 接口 | `POST /embed`，body: `{texts[], return_dense, return_sparse, batch_size}` |
| dense 向量 | **1024 维** |
| sparse 向量 | `{token_id: weight}`，中等长度文本约 **33 个非零项** |
| 吞吐 | **约 360 条/秒**（256 条一批） |
| 单批上限 | **256 条**（超出返回 400） |
| 入库估算 | 20 万 chunk ≈ **10 分钟** |

**关键价值**：BGE-M3 同时输出 dense + sparse，**sparse 向量即词权重，可直接做关键词检索**。这意味着我们**不需要部署 Elasticsearch**，Milvus 原生的 dense+sparse 混合检索即可实现向量+关键词双路召回。

### 3.2 与原方案（豆包版）的差异说明

| 项 | 原方案 | 本计划 | 修订理由 |
| :--- | :--- | :--- | :--- |
| 向量库 | Chroma | **Milvus** | 1000–10000 篇量级，Chroma 并发与规模上限不足 |
| 检索方式 | 纯向量 | **dense + sparse 混合** | BGE-M3 免费提供 sparse，召回率显著优于纯向量 |
| 关键词检索 | Elasticsearch BM25 | **不需要** | BGE-M3 sparse 向量已覆盖词权重能力，省掉整个 ES |
| Embedding | bge-large-zh-v1.5 | **bge-m3（已有服务）** | 更优，且已部署在 GPU 上，无需本地安装 |
| LLM | vLLM + Qwen3-8B | **已有的 Qwen3-27B-FP8** | 实测已在跑，无需自建；质量更好但速度更慢 |
| OCR | PaddleOCR | **暂不引入（可插拔）** | 确认无扫描件需求，避免重型依赖 |
| Rerank | 未提及 | **暂不引入（可插拔）** | 二期按评测数据决定 |
| 响应指标 | 5 秒 | **首字 1.5s + 流式** | 21.3 tok/s 硬件约束，见 1.4 |

**后端**

| 组件 | 选型 | 说明 |

## 五、分阶段开发计划

### 阶段 1：后端骨架 + 文档入库 + 混合检索

**目标**：打通"文档 → chunk → 向量 → 检索"链路，用命令行脚本验证召回质量。

| # | 任务 | 交付物 |
| :--- | :--- | :--- |
| 1.1 | 项目脚手架、配置管理、日志体系 | `backend/` 目录骨架 |
| 1.2 | Embedding 客户端封装（bge-m3，dense+sparse，自动分批 256） | `app/services/embedding.py` |
| 1.3 | Milvus 客户端封装（collection 建表、upsert、混合检索、RRF 融合） | `app/services/vectorstore.py` |
| 1.4 | 文档解析器（PDF/DOCX/XLSX/PPTX/HTML/MD/TXT） | `app/services/parsers/` |
| 1.5 | 分块策略（递归分块 + 标题路径保留 + 表格保护） | `app/services/chunker.py` |
| 1.6 | SQLite 数据层（文档、chunk、会话、消息、日志） | `app/models/` + `app/db.py` |
| 1.7 | 入库流水线（异步、断点续传、状态追踪） | `scripts/ingest.py` |
| 1.8 | 检索评测脚本（召回率、MRR、延迟） | `scripts/eval_retrieval.py` |

**验收标准**：
- 用 5–10 篇真实文档入库成功，Milvus 中可见对应向量
- 检索脚本能返回带 dense/sparse 双分数的结果
- 20 条测试问题的人工相关性评分 ≥ 80%
- 检索 P95 延迟 < 300ms

## 七、核心接口契约（概要）

| 方法 | 路径 | 说明 |
| :--- | :--- | :--- |
| POST | `/api/document/upload` | 多文件上传，返回任务 ID |
| GET | `/api/document/list` | 文档列表（分页/筛选） |
| DELETE | `/api/document/{id}` | 删除文档及其向量 |
| POST | `/api/document/{id}/reparse` | 重新解析 |
| GET | `/api/chat/stream` | **SSE** 流式对话（query + session_id） |
| GET | `/api/conversation/list` | 会话列表 |
| DELETE | `/api/conversation/{id}` | 删除会话 |
| GET | `/api/log/query` | 日志分页查询 |
| GET | `/api/log/stats` | 统计数据 |
| GET | `/api/log/unmatched` | 高频未命中问题 |
| GET/PUT | `/api/config` | 系统配置读写 |

> **✅ 2026-09-06 已实现**（步骤 5 + 步骤 8）：`GET /api/chat/stream`（SSE，带 `question` / `conversation_id` / `kb_id` / `mode`，事件序 meta → references → delta×N → done / error）、`GET/POST /api/conversations`、`DELETE /api/conversations/{id}`、`GET /api/conversations/{id}/messages`、`POST /api/documents`（multipart 多文件上传）、`GET /api/documents`（分页/搜索/状态筛选）、`DELETE /api/documents/{id}`（删除补偿）、`POST /api/documents/{id}/reprocess`、`GET/POST /api/kbs`、`GET /api/logs/files`、`GET /api/logs/entries`（倒序分页+级别/关键词筛选）、`GET /api/logs/download`、`GET /api/stats/summary`（days/mode 口径）、`GET/PUT /api/config/params`（白名单 10 项+自动重启）、`GET /api/config/system`、`GET /api/config/diagnostics`。阶段 3 全部 API 已闭环。

**SSE 事件格式**：

```
event: references      # 先推送引用来源，前端提前渲染
data: {"sources":[{"doc_name":"...","chunk_id":"...","score":0.87,"text":"..."}]}

event: delta           # 逐字推送
data: {"content":"根"}

event: done            # 结束，携带统计
data: {"session_id":"...","message_id":"...","elapsed":12.3,"tokens":256}
```

> 先推引用再推正文是刻意设计：用户看到答案的同时就能看到来源，不必等生成结束。

## 八、风险清单

| # | 风险 | 等级 | 影响 | 应对措施 |
| :--- | :--- | :--- | :--- | :--- |
| **R1** | **Milvus 实例共享风险**：现有实例已有 372 万向量（docmind 项目），且其检索接口实测连续两次 **280 秒超时**，状态不健康 | 🔴 高 | 检索延迟不可控，直接影响全部指标 | **建议独立部署 Milvus**。阶段 0 先做延迟验证，若 P95 > 500ms 则必须独立部署 |
| **R2** | **LLM 吞吐受限**：21.3 tok/s，并发上升时人均速度下降 | 🟡 中 | 多人同时使用时体验下降 | 当前 1–5 人可控；后端内置并发信号量（默认 3），超出排队并提示；代码层预留扩容能力 |
| **R3** | **内网离线部署的前端依赖**：目标服务器可能无外网 | 🟡 中 | 无法 npm install | 在可联网环境 `npm ci` 后打包 `node_modules`，或 `npm pack` 导出 tarball，一并拷贝 |
| **R4** | **Windows 开发 / Linux 部署差异**：路径分隔符、文件编码、换行符 | 🟡 中 | 部署后运行异常 | 全程使用 `pathlib`，显式 UTF-8，`.gitattributes` 统一 LF，Docker 内验证 |
| **R5** | **表格解析质量**：混合类型文档中表格是 RAG 难点 | 🟡 中 | 表格类问题答不准 | 表格转为 Markdown 并整体保留不切分；阶段 4 专项调优 |
| **R6** | **中文检索召回**：专业术语、缩写、口语化提问 | 🟢 低 | 部分问题召回失败 | BGE-M3 sparse 分支已大幅缓解；阶段 4 用真实数据建评测集量化 |
| **R7** | **LLM 服务单点**：221 服务器故障则系统不可用 | 🟢 低 | 整体不可用 | 后端做健康检查与友好降级提示；配置层支持快速切换备用端点 |
