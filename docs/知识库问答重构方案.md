# 知识库问答（KB QA）重构方案

> 状态：**待确认**（用户评审通过后开工）
> 范围：前端体验重设计 + 后端配套增强（多轮对话、跨库检索、智能检索、推荐问题、相关问题、反馈收集、会话搜索、引用跳转文档预览、权限模型）
> 参考气质：豆包交互；视觉保持现有浅色简洁风

---

## 一、背景与目标

现有知识库问答功能"能跑但简陋"：

- 空状态无引导，新用户进入不知道该问什么；
- 多轮追问死板：检索始终用"原始问题"，追问（如"那 2024 年呢"）几乎必然无命中；
- 会话仅绑单库、无跨库检索；聊天页没有知识库选择器；
- 消息无复制/重新生成/反馈闭环；
- 引用按 chunk 平铺、无法跳转原文预览；
- 会话无搜索、无置顶。

本次重构目标：**把问答从"可用"提升为"好用的企业内部多轮对话式 RAG"**，并配套可落地的权限与反馈体系。

## 三、权限模型：知识库成员制

### 3.1 规则

| 概念 | 定义 |
|---|---|
| 全局角色 | 保留现有 users.role：`admin` = 超级管理员（可见/管理所有库）；`editor` / `viewer` 语义**不再单独决定库权限**（见下） |
| 知识库成员 | 新表 `kb_members(kb_id, user_id, role)`；role ∈ `owner / editor / viewer` |
| owner | 创建库的人自动成为 owner；可管理成员、可编辑 |
| 可见性 | 全局 admin 或 该库成员清单内 → 可见（文档管理页、聊天页选择器、检索均按此过滤） |
| 库内权限 | owner/editor：上传、删除、重命名、移动、重处理；owner：成员管理；viewer：只读（问答、预览、下载） |

### 3.2 关键点

- 不引入部门表/字段，满足"多部门隔离 + 跨部门协作"：一个人可在不同库拥有不同角色；
- 权限判定一处收敛：后端统一 dependency（`require_kb_member / require_kb_editor / require_kb_owner`），前端按接口 403/过滤结果渲染；
- 现有全局 editor/viewer 角色保留但降级为"默认角色"，仅作新用户初始角色参考；知识库权限以成员清单为准。

### 3.3 接口

- `GET /api/kbs`：按当前用户过滤可见库（含 role 标注，供前端渲染管理入口）
- `GET /api/kbs/{kb_id}/members`：成员列表（owner/admin）
- `PUT /api/kbs/{kb_id}/members/{user_id}`：添加/调整成员角色（owner/admin）
- `DELETE /api/kbs/{kb_id}/members/{user_id}`：移除成员（owner/admin，不可移除自己/最后一个 owner）
- 文档管理各接口加权限依赖

### 3.4 权限矩阵与授权边界

权限必须由后端在每一个读写入口校验，前端隐藏按钮不视为安全措施。

| 操作 | admin | owner | editor | viewer |
|---|---:|---:|---:|---:|
| 查看知识库、文档、文件夹 | 全部 | 成员库 | 成员库 | 成员库 |
| 问答、智能检索、预览、下载 | 全部 | 成员库 | 成员库 | 成员库 |
| 上传、删除、移动、重处理 | 全部 | 是 | 是 | 否 |
| 管理成员 | 全部 | 是 | 否 | 否 |
| 删除知识库 | 全部 | 否（可申请转交） | 否 | 否 |

- `kb_ids` 未提供：检索当前用户全部可见库。
- `kb_ids=[]`：表示明确不检索，返回 422；不能被解释为“全部可见库”。
- `kb_ids` 含不可见库：返回 403，不静默扩大或改变用户的检索范围。
- 所有文档列表、预览、下载和向量检索接口都必须使用同一个 `effective_kb_ids` 解析器。
- 不能删除或降级知识库最后一个 owner；owner 转移与成员变更必须在同一事务内完成。

### 3.5 存量数据回填

`kb_members` 上线迁移必须包含一次性回填和幂等规则：

- `default` 知识库：现有 admin 自动建立 owner；现有 editor 建立 editor；viewer 建立 viewer。
- 其他已有知识库：按其创建记录或部署配置确定 owner；无法确定时只允许 admin 接管并记录告警。
- 已存在但没有成员的知识库不得被普通用户自动发现。
- 删除用户、删除知识库时明确 FK 策略（建议成员记录级联删除，业务数据保留软删除/审计记录）。

## 四、前端设计

### 4.1 页面布局

```
聊天页（ChatView）
├─ 左侧 会话侧边栏（增强）
├─ 中间 主区：空状态 或 消息流 + 输入区
└─ 右侧 文档预览面板（抽屉，随用随开，可关闭）
```

### 4.2 会话侧边栏

- 顶部搜索框：防抖 300ms 调 `GET /conversations/search?q=`（标题+消息内容），显示匹配会话（命中的消息摘要高亮）；
- 分组：置顶组（☆）在上、普通组在下；新建会话按钮置顶；
- 会话项：标题 + 所属知识库小标签（当前会话最近使用库）；hover 显示气泡菜单：置顶/取消置顶、重命名、删除；
- 重命名/删除：**复用现有能力**，弹窗/气泡交互轻量化（小号 popover，删除保留二次确认）；
- 切库不影响会话归属（会话不绑库）。

### 4.3 空状态（无消息时）

- 欢迎语 + 简短能力说明（"基于企业知识库的问答助手，支持多库检索与多轮追问"）；
- **推荐问题**区：展示当前所选知识库的推荐问题（卡片列表），点击即作为问题发送（带上当前选择的知识库）；无缓存时显示"生成中…"；
- **最近会话**：最近 5 条会话入口，点击进入。

### 4.4 消息卡片

**用户消息**：气泡样式（现状保留）。

**AI 消息卡片**：
- Markdown 正文（`[n]` 引用锚点，现状保留）；
- 操作行（正文下方）：
  - **复制**：`navigator.clipboard` 复制 Markdown 原文，提示"已复制"；
  - **重新生成**：以相同问题 + 原回答版本记录的检索范围重新生成，创建新的回答版本（生成中显示流式光标；新版本反馈为空，旧版本保留审计）；
  - **点赞 / 点踩**：单选切换；点踩展开原因输入区（选填，鼓励填写），提交后置灰，`POST /feedback` 落库；
- 状态行：检索/生成耗时、停止生成、错误重试（现状保留）。

### 4.5 引用来源与文档预览

- 引用按**文档聚合**展示：`来源文件（N）` 列表，每项 = 文件图标 + 文件名 + 命中页数/次数 + 最高相似度；
- 点击文件项 → 展开该文档的 chunk 摘要列表（复用现有引用卡片交互：hover 浮窗、正文锚点高亮）；
- 文件项右侧"查看原文" → 打开**右侧预览面板**（PDF/图片/TXT，复用 `FilePreviewDialog` 渲染逻辑，改为抽屉形态，支持按页懒加载/进度）。

### 4.6 相关问题

- 知识库模式且有命中、生成完成后，答案下方显示"继续追问"区：2~3 个胶囊按钮；
- 点击任意一个 → 直接作为新问题发送（走正常检索+生成流程）；
- 数据来源：`done` 事件携带 `related_questions`（不落库，刷新历史会话后不再显示）。

### 4.7 输入区增强

- **知识库选择器**：多选下拉（`el-select multiple collapse-tags`），选项 = 当前用户可见库（带文档数），含"全部可见库"快捷项；选择结果作为 `kb_ids` 随每次提问提交（会话不绑库）；
- 模式切换（知识库问答 / 通用问答）、语音输入、发送/停止：现状保留。

### 4.9 智能检索页面

智能检索是独立于聊天问答的“找文件 / 找原文”工作台，默认只返回用户有权访问的知识库内容，不调用 LLM 生成答案。

#### 页面布局

```
智能检索页（IntelligentSearchView）
├─ 顶部：搜索框 + 搜索按钮 + 搜索模式
├─ 条件栏：知识库多选、文件类型、文件夹、时间范围、状态
├─ 主区：结果列表（按文档聚合）
└─ 右侧：文档预览抽屉（复用 FilePreviewPanel）
```

#### 搜索模式

- **语义检索**：问题或自然语言描述 → dense embedding → 向量召回。
- **关键词检索**：精确词、文件名、标题、正文关键词 → 中文 ngram/FULLTEXT 或可插拔文本索引；文件名等结构化字段使用独立索引，不依赖全文分词。
- **混合检索**：dense + keyword 分别召回，使用 RRF 融合；结果中同时展示语义分数和关键词命中信息。
- 模式是显式选择，不自动把“关键词检索”当作聊天问答；用户可以切换模式后保持原查询和筛选条件。

#### 结果交互

- 结果按文档聚合，展示文件名、所属知识库、文件夹路径、命中次数、最高分、匹配页码和状态。
- 展开文档查看命中片段，关键词模式对命中词做高亮；语义模式展示相似度和片段上下文。
- 点击“查看原文”打开右侧预览抽屉，并定位到命中页；预览和下载再次校验知识库成员权限。
- 支持复制片段、打开聊天并带入“基于该片段继续提问”；带入聊天时保存 `source_doc_id/source_chunk_id`，不能只传任意文本。
- 空结果显示当前过滤条件和可调整建议；不得泄露不可见知识库、文档名称或命中数量。
- 结果必须分页或游标加载，默认 20 条，最多 100 条；前端不得一次拉取全库结果。

#### 条件与状态

- 知识库选择器复用聊天页的可见库列表；“全部可见库”只代表服务端解析出的有效集合。
- 支持文件扩展名、文件夹、文档状态、更新时间范围筛选；筛选条件通过结构化参数传递，不拼接查询字符串。
- 搜索请求显示耗时、召回数量和索引状态；索引不可用时明确提示降级路径，不静默返回空结果。

## 五、后端设计

### 5.1 多轮对话管线（查询改写）

```
当前问题 + 会话历史
  ├─ 历史为空 → 直接用原问题检索
  └─ 历史非空 →
       ① 查询改写：轻量 LLM 调用
          system: "结合对话历史，把用户的追问改写成可独立检索的查询。
                   只输出改写后的查询文本，不解释。"
          （失败 / 超时 → 回退原问题，不影响主流程）
       ② 用【改写后 query】跨库检索（kb_ids 多选或全部可见库）
       ③ prompt = 原问题 + 历史 + 检索结果（sources 带 kb_id 标注）
       ④ 流式生成
       ⑤ 有命中 → LLM 生成相关问题（随 done 返回，不落库）
```

要点：
- 改写用独立轻量调用（小 max_tokens），失败静默回退；
- 改写前限制历史轮数和 token 预算，改写结果限制最大长度、去除空结果；失败、超时或结果异常时回退原问题；
- 改写后的 query、模型、耗时、状态和原问题一起记录到 query_log，便于排查检索效果；
- 改写只用于检索，不覆盖用户原问题；回答 prompt 仍使用原问题和受限历史；
- 检索接口接收服务端解析出的 `effective_kb_ids`，禁止直接信任客户端的知识库列表；
- 多库检索使用 `kb_id in (...)` 的向量过滤或受控分库召回，再统一 RRF；sources 中必须带 `kb_id`；
- 限制单次最多选择的知识库数量、召回总量和上下文字符预算，避免跨库请求放大成本。

### 5.2 SSE v2 协议（POST /api/chat/stream）

| 事件 | 变更 |
|---|---|
| `meta` | 不变 |
| `references` | `sources[]` 增加 `kb_id` 字段 |
| `delta` | 不变 |
| `related` | **新增**：`{"questions": ["...", "..."]}`（kb 模式且有命中时下发；失败不影响主回答） |
| `done` | 携带 `request_id`、`message_id`、耗时、命中数和 `message_type`；必须是最后一个业务事件 |
| `error` | 不变 |

请求使用 POST JSON，避免把问题和知识库选择写入 URL 日志。参数：

```json
{"request_id":"...", "question":"...", "conversation_id":"...",
 "kb_ids":["kb_a","kb_b"], "mode":"dense"}
```

`kb_ids` 缺省表示全部可见库，空数组返回 422；服务端返回 `effective_kb_ids` 供审计。每个事件带 `request_id` 和递增 `seq`，取消、断线、重复提交和错误均有明确状态。

### 5.3 接口清单

| 接口 | 说明 |
|---|---|
| `POST /api/chat/stream` | 增强：kb_ids 多选、query rewrite、related 事件和可取消请求 |
| `POST /api/feedback` | 只接收 `message_revision_id/feedback/reason`；问题、答案和知识库范围由服务端反查 |
| `GET /api/conversations/search?q=&cursor=` | 标题+消息内容匹配，按用户过滤、分页并返回命中摘要 |
| `GET /api/recommended/questions?kb_id=` | 返回缓存和生成状态；无缓存只创建幂等任务，不在请求内直接跑 LLM |
| `POST /api/recommended/questions/refresh?kb_id=` | 手动重新生成 |
| `GET /api/kbs/{kb_id}/members`、`PUT/DELETE /api/kbs/{kb_id}/members/{user_id}` | 成员管理（owner/admin） |
| `GET /api/kbs` | 按可见性过滤 + 角色标注 |
| `POST /api/search` | 智能检索：语义 / 关键词 / 混合模式，返回分页文档结果和命中片段 |
| `GET /api/search/index-status` | 返回当前用户可见库的索引状态和降级信息 |

### 5.4 推荐问题生成（持久化异步任务）

- 触发：启动时只创建缺失缓存的幂等任务 + 前端手动刷新按钮；Web 进程不直接承担长任务，使用持久化任务表/任务队列；
- 逻辑：对**尚无缓存**的知识库，从向量库/DB 抽样文档 chunk → LLM 生成 5~8 条代表性提问 → 落 `recommended_questions` 表；
- 约束：逐库串行、走 `_llm_semaphore` 限流，避免打满 LLM；
- 上传新文档后**不自动重生成**（手动刷新）。
- 每个知识库同时只能有一个 `pending/running` 任务；任务记录开始时间、结束时间、错误信息、重试次数和内容版本；
- 多 worker / 多实例通过数据库锁或队列去重，进程重启后可恢复未完成任务；
- 手动刷新使用版本号或显式 `force=true`，不能覆盖正在运行的任务。

### 5.5 反馈收集

- `POST /api/feedback` 校验当前用户对 message revision 的归属后落库；
- 同一用户对同一回答版本只能有一条有效反馈，重复提交采用 upsert；
- 重新生成创建新回答版本，旧版本及其反馈保留审计记录，不物理覆盖；
- 本期只存不做管理查看页，但保留导出和后续统计所需字段。

### 5.6 会话搜索

- `GET /api/conversations/search?q=&cursor=`：按用户过滤，返回有上限的分页结果；
- 初期可使用 MySQL FULLTEXT，数据规模较小时允许 LIKE fallback；禁止无上限全表扫描；
- 明确搜索用户消息、助手消息或两者，转义 `%` / `_`，并统一摘要截断和高亮规则；
- 置顶和最近活动排序必须有稳定的二级排序键，避免分页重复或漏项。

### 5.7 权限接入点

- 新增统一依赖：`require_kb_member(kb_id)` / `require_kb_editor(kb_id)` / `require_kb_owner(kb_id)`；
- 文档列表、预览、下载、上传、移动、删除、重处理、成员管理接口挂载对应依赖；
- 聊天和智能检索先解析 `effective_kb_ids`，再把该集合传入 SQL/Milvus 过滤条件；
- 不可见库不得静默转换成全部可见库；显式传入不可见库时返回 403；
- 创建知识库与创建 owner 成员必须在同一事务内完成。

### 5.8 智能检索后端设计

#### 请求与权限

```json
{
  "query": "合同中关于违约责任的约定",
  "mode": "semantic|keyword|hybrid",
  "kb_ids": ["kb_a", "kb_b"],
  "folder_id": null,
  "file_types": ["pdf", "docx"],
  "status": "done",
  "updated_after": null,
  "updated_before": null,
  "cursor": null,
  "limit": 20
}
```

- 服务端校验 query 长度、limit、文件类型和时间范围；最多返回 100 条；
- `kb_ids` 先解析成 `effective_kb_ids`，所有模式共用同一权限结果；
- 不返回不可见库的文档名、数量、分数或“无结果”差异提示。

#### 检索与排序

- 语义模式：调用现有 embedding + Milvus dense search，过滤 `kb_id in effective_kb_ids`。
- 关键词模式：中文环境优先使用配置过 ngram/tokenizer 的 MySQL FULLTEXT；若语料规模或分词效果不达标，替换为 OpenSearch 等独立文本索引，接口不暴露实现细节。
- 混合模式：两路分别取候选，使用 RRF 融合；记录 `dense_score`、`keyword_score`、`fused_score`，不把不同量纲的原始分数直接比较。
- 结果先按 `doc_id` 聚合，再取最高分和命中片段；同一文档最多返回固定数量片段，避免单文档挤占结果。
- 只检索 `status=done` 且索引已完成的文档；索引缺失时返回 `index_status` 和可解释的降级信息。

#### 返回结构

```json
{
  "items": [{
    "doc_id": "...", "kb_id": "...", "file_name": "...",
    "folder_path": "...", "hit_count": 3, "max_score": 0.87,
    "matches": [{"chunk_id":"...", "page":4, "text":"...", "score":0.87}]
  }],
  "next_cursor": "...",
  "total": null,
  "effective_kb_ids": ["kb_a", "kb_b"],
  "index_status": "ready"
}
```

智能检索只负责找资料，不生成答案；“带入聊天”必须通过服务端签发的 `doc_id/chunk_id` 引用，聊天接口再次校验权限。

## 九、问数智能体规划（M5，下一期）

> 定位：问答从"单路径"升级为"意图路由 + 工具调用"。本期（M1~M4）**不实施**，但架构预留扩展点，避免将来推倒重来。

### 9.1 目标形态

```
用户问题
  ├─ 意图路由（自动判断，用户无需手动切模式）
  │   ├─ 普通闲聊/常识      → 通用问答工具（已有 general）
  │   ├─ 知识库文档问题      → RAG 工具（已有 dense/hybrid）
  │   └─ 数据/业务问题      → 问数工具（新增）
  │       └─ 数据源注册表 → schema 上下文 → NL2SQL 生成
  │           → 只读校验 → 执行 → 结果转述（表格/图表）→ 审计
```

### 9.2 数据源注册表（新表，M5 建）

| 字段 | 说明 |
|---|---|
| `data_sources` | id, name, type(mysql 起步), host, port, database, username(**只读账号**), password(加密存储), tables(表白名单 JSON), description, enabled, created_at |

- 只读账号：`GRANT SELECT ON ...`，从数据库侧杜绝写操作；
- 表白名单：只有注册的表可查，未注册表直接拒绝。
- 凭据不能明文落库或回显；使用部署环境的密钥管理能力加密，支持轮换和吊销；
- 数据源连接池与主业务数据库隔离，按数据源限制连接数、超时和返回字节数。

### 9.3 NL2SQL 管线（M5）

1. schema 上下文：从注册表加载表结构（列名/类型/注释）+ 示例值 → 进 prompt；
2. SQL 生成：LLM 生成 SELECT；
3. **只读校验（硬规则）**：
   - 使用 SQL AST 校验而不是简单字符串匹配；仅允许只读 SELECT，拒绝多语句 / `INFORMATION_SCHEMA` / 系统库 / `INTO OUTFILE` / 用户变量 / 写入函数等；
   - 强制 `LIMIT`（默认 100，上限 500）、强制超时（如 10s）；
   - 执行连接使用数据库侧只读账号，并设置 statement timeout、最大返回行数和最大返回字节数；
   - 校验失败 → 友好报错，不执行；
4. 执行（只读连接池）→ 结果集；
5. 结果转述：自然语言总结 + **表格 + 简单图表**（趋势/占比用 ECharts）；
6. 审计：谁、何时、问题、生成 SQL、行数 → 落库（query_log 扩展或独立 data_query_log）。

### 9.4 权限（按用户已确认）

- 库级 / 表级白名单即可，不做列级脱敏（后续可按需扩展）；
- 问数权限与 kb_members 解耦，独立配置（数据源 → 可用用户/角色）。

### 9.5 多轮

- 问数上下文：上一轮 SQL / 结果集摘要进 prompt，支持"那环比呢""按部门分呢"这类追问。

### 9.6 本期架构预留点（M1~M4 落地时留好）

| 位置 | 预留 |
|---|---|
| SSE 协议 | `done` 事件预留 `message_type` 字段（text / table / chart），本期恒为 text |
| 消息模型 | 前端消息类型预留 `content_kind`（text/markdown/table/chart），本期仅 markdown |
| 模式参数 | `mode` 参数预留 `agent`（自动路由）枚举值，本期不开放 |
| 路由位置 | 后端 `answer_stream` 保持单入口事件流，M5 在入口处加意图路由分发，不改调用方 |
| 查询日志 | `query_log` 预留 `tool` 字段（rag / general / data_query），本期写 rag/general |
