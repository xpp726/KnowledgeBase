## 1. 分层依赖方向

```
HTTP / SSE 请求
      ↓
① api/ 层        路由 · 参数校验 · SSE 协议 · 错误映射（不写业务，不直连 db）
      ↓
② services/ 层   业务编排（ingestion / retrieval / rag / document / conversation / tasks）
      ↓
③ 数据访问 + 外部客户端
   models(SQLAlchemy ORM) · embedding · vectorstore · llm · storage 实现
      ↓
MySQL（唯一） · Milvus（kb_id 过滤） · MinIO · BGE-M3 · LLM
```

约束：
- api 不直连 db / 外部服务；services 不 import FastAPI；外部客户端只做协议转换、不含业务规则。
- services 之间可互相调用。

## 4. 数据模型变更

| 表 | 现状 | 变更 |
|---|---|---|
| knowledge_bases | 无 | 新增：kb_id PK, name, description, created_at |
| documents | 无 kb 维度 | + kb_id（FK）；file_path 语义改为对象存储 key；status 状态机扩展 |
| chunks | 5 字段 | + kb_id（与 Milvus 行对齐） |
| conversations | 无 kb 维度 | + kb_id（会话挂知识库） |
| messages | 有 refs_json | 不变（kb_id 走会话关联） |
| query_logs | 有统计字段 | + kb_id |
| 二期 | — | users / 权限表（user_id 届时补，本期不加） |

**documents.status 状态机**：pending → ingesting → embedding → done；失败 → failed（带 error）；启动扫描 stuck（超时阈值）→ 标记 failed 或重跑。

**删除补偿**：删文档 = ① Milvus 向量 → ② MinIO 文件 → ③ DB 记录；每步成功才进下一步，失败写补偿日志，scripts/cleanup.py 兜底。

**日志持久化**：日志统一落盘 `data/logs/`（LOG_DIR 可覆盖，相对路径以 backend 根解析）。`app/log_config.py` 用 dictConfig 构建双输出：console（开发期实时观察）+ 文件（按天轮转，保留 LOG_RETENTION_DAYS 天）；业务日志与 HTTP 访问日志分离为 `app.log` / `access.log`（避免两个 handler 写同一文件在轮转时竞争）；第三方库（sqlalchemy/httpx/urllib3/pymilvus）默认 WARNING 降噪，排障时调 LOG_LEVEL=DEBUG。业务代码全程 `logging.getLogger(__name__)`，经 root 自动落文件，无需改动业务代码。**必须经 `python -m app.run` 启动**（run.py 注入日志配置），裸 `uvicorn app.main:app` 会被 uvicorn 默认配置覆盖、只输出到控制台。

**时间戳列类型（2026-09-13 最终约定 DATETIME）**：
- **陷阱**：SQLAlchemy 将 `Mapped[float]` 默认映射为 MySQL **FLOAT（单精度，约 7 位有效数字）**；在 17 亿级时间戳下分辨率仅约 ±128s，user/assistant 消息写入时间差会被舍入成同值，导致消息顺序不稳（"先答后问" bug 的数据层根因）。
- **约定（最终版）**：所有时间戳列统一使用 **DATETIME**（本地时间 naive，与 Python `datetime.now()` 一致），与 ASR 项目对齐。模型层 `Mapped[datetime]` + `DateTime`（`default=datetime.now`/`onupdate=datetime.now`）；API 层 Pydantic 输出 ISO 字符串；前端 `Date.parse(iso)`。**不再使用 float/DOUBLE 秒浮点**。
- **存量迁移**：kb 库 14 个时间戳列已 DOUBLE → DATETIME 无损完成（`datetime.fromtimestamp` 本地时区语义；`<=0` 值转 NULL）；新环境由 create_all 直接建 DATETIME 列。

## 8. 权限体系一期（步骤 9，已实施）

### 8.1 设计决策

| 维度 | 决策 | 依据 |
|---|---|---|
| 认证方式 | 内置用户名/密码（不做 LDAP/OAuth） | 内网部署，用户量 5-10 人，内置足够 |
| 密码哈希 | bcrypt（直接用 bcrypt 库，不用 passlib） | passlib 已停止维护且与 bcrypt 5.0 不兼容 |
| Token | JWT HS256，24h 过期 | 无状态，允许多端登录，不做服务端 session |
| 角色粒度 | 三级 admin/editor/viewer | 覆盖典型场景，不过度设计 |
| 会话隔离 | conversations.user_id 过滤，非本人返回 404 | 不暴露会话存在性（安全原则） |
| 默认账号 | 首次启动自动创建 admin/admin | 降低部署门槛，display_name "系统管理员" |
| 数据迁移 | ensure_schema_patches() 幂等 ALTER TABLE | 仅 MySQL（information_schema 检测列存在） |

### 8.5 关键实现细节

**1. ensure_default_admin()**：lifespan 启动时检查是否有 active admin，无则创建默认 admin/admin。逻辑是"检查是否有 active admin"而非"表为空"，避免测试数据残留导致 admin 未创建。

**2. FastAPI 依赖**：
- `get_current_user`：从 Authorization: Bearer 解析 JWT，查库确认用户存在且 is_active
- `require_admin`：get_current_user + role==='admin'
- `require_editor`：get_current_user + role in ('admin','editor')

**3. 自我保护逻辑**（users_api PUT）：
- 禁止禁用自己（is_active=false 且 id==current_user.id → 400）
- 禁止降低自己角色（admin→editor/viewer → 400）

**4. 测试隔离**：测试统一用共享 MySQL kb_test 库（conftest 将 app.db engine 替换为 NullPool，规避 asyncmy 跨事件循环坑）；每用例开始前清空业务表并 ensure 默认 admin、结束后再清一次，模拟独立库隔离。
