### 4.3 SSE 事件契约（实读后端 api/chat.py 确认）

帧格式：`event: {name}\ndata: {json}\n\n`（无注释行 /id/retry / 多行 data）。



| 事件           | 字段                                                                      | 时序                                 |
| ------------ | ----------------------------------------------------------------------- | ---------------------------------- |
| `meta`       | `conversation_id`、`is_new`                                              | 首个事件                               |
| `references` | `sources: [{index, chunk_id, doc_id, doc_name, page, score, text}]`     | meta 后、delta 前（无命中时 sources 为空）    |
| `delta`      | `content`                                                               | 多次，流式文本                            |
| `done`       | `conversation_id, message_id, hit_count, elapsed, retrieval_ms, llm_ms` | 最后（**error 后仍会补发**，message\_id=""） |
| `error`      | `stage`、`message`                                                       | 任意阶段可插入，之后仍有 done                  |

> ⚠️ 两个必须处理的契约细节：① error 后仍会收到 done，前端以 "是否出现过 error" 为准决定消息固化方式；② 无命中时后端不发 LLM（llm_ms=0），
>
> `references.sources=[]`
>
>  \+ 固定话术，前端用 
>
> `hit_count===0`
>
>  区分空态样式。
>
> **mode=general（通用问答）**：后端跳过检索直接 LLM 流式——不发 `references` 事件；`done` 固定 `hit_count=0`、`retrieval_ms=0`，仅 `llm_ms` 有效；user/assistant 照常落库。前端按**会话模式**（store.currentMode）渲染，不依赖 hit\_count 判断。

## 5. SSE 消费设计（手写解析器）

### 5.1 选型归档（A1）



| 方案                            | 本项目结论                                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------- |
| 原生 EventSource                | ❌ 弃用。断线**自动重连 = 重发请求**，而本端点是有副作用的 GET（落库 user 消息、可能新建会话），会重复提交；且看不到状态码、4xx/5xx 也会无限重试        |
| fetch+ReadableStream 手写       | ✅ 采用。需要的能力（abort / 超时 / 错误码 / 不自动重连）fetch 原生全有，帧格式极简（无 id/retry/ 注释 / 多行 data），\~50 行 TS 可覆盖 |
| @microsoft/fetch-event-source | ❌ 不引入。其内置重试语义与 "有副作用端点" 冲突，需额外理解并关闭；本项目单端点、GET、无 header，库价值用不上                               |

### 5.2 `api/sse.ts` 接口与算法



```
// 解析器对外接口（纯函数/类，不依赖 store）

export interface SseHandlers {

&#x20; onOpen?: () => void                       // 响应头到达、200 校验通过

&#x20; onEvent: (event: string, data: unknown) => void  // 按 event 名分发（meta/references/delta/done/error）

&#x20; onClose?: () => void                      // 正常结束（done 后或流自然结束）

&#x20; onError?: (err: SseError) => void         // 网络/HTTP/超时/abort 归一化错误

}

export interface SseClient {

&#x20; abort(reason?: string): void              // 停止生成（B1）

&#x20; readonly done: Promise\<void>              // 供调用方 await 收尾

}

export function createSseClient(

&#x20; url: string,

&#x20; handlers: SseHandlers,

&#x20; opts?: { timeoutMs?: number; signal?: AbortSignal },  // 默认 60\_000（B3）

): SseClient
```

分帧算法（核心，vitest 必测）：



1. `fetch(url)` → 校验 `response.ok`，否则 `onError({kind:'http', status})`；

2. `response.body.getReader()` + `TextDecoder('utf-8', {stream:true})` 解码（**必须 stream:true**，否则中文字符被 TCP 分片截断会丢字 / 乱码）；

3. buffer 累积，按 `\n\n` 切出完整帧，残帧留到下一轮拼接；

4. 每帧按行解析：`event: X` 行定事件名（缺省 `message`），`data:` 行 JSON.parse（单行）；

5. 60s 内无任何新字节 → abort + `onError({kind:'timeout'})`；`onError` 后不再分发事件。

**不自动重连**：任何终局（done /error/abort / 超时）之后，客户端不发起新请求；重试由 UI 层手动触发（B3）。

### 5.3 `api/chat.ts`



```
export interface StreamChatParams {

&#x20; question: string

&#x20; conversationId?: string | null

&#x20; kbId?: string            // 固定传 'default'（D2），代码留位

&#x20; mode?: 'dense' | 'hybrid' | 'general'   // 前端映射：知识库→dense；通用→general（hybrid 留 API 层）

```

职责：URLSearchParams 组装 → 调 `createSseClient` → 透传 handlers。不做状态管理。

### 5.4 三种终局语义（供 store 消费）



| 终局   | 触发                               | store 动作                                    |
| ---- | -------------------------------- | ------------------------------------------- |
| 正常完成 | 收到 done 且无 error                 | 固化消息（message\_id / 耗时），state→idle           |
| 用户停止 | 点停止 → `client.abort()`           | 本地补 "⏹ 已停止生成" 占位（不写库，B1），state→stopped→idle |
| 失败   | error 事件 / HTTP 非 200 / 超时 / 网络断 | 错误气泡 + 重试按钮（B3），state→error→idle            |

## 6. 状态与数据流（B・全并 store）

### 6.1 chat store 状态



```
interface ChatState {

&#x20; conversations: Conversation\[]          // 侧栏列表（按 updated\_at 倒序；按当前模式过滤）

&#x20; currentMode: 'kb' | 'general'         // 问答模式（下拉）：kb=知识库问答 / general=通用问答；会话按模式隔离（方案 A）

&#x20; currentId: string | null

&#x20; messages: MessageItem\[]                // 当前会话消息（含流式中的临时消息）

&#x20; streamState: 'idle' | 'connecting' | 'streaming' | 'stopped' | 'error'

&#x20; controller: AbortController | null     // 当前流控制柄（停止/超时共用）

&#x20; pendingQuestion: string | null         // 供重试（B3）

}

interface MessageItem {

&#x20; localId: string

&#x20; role: 'user' | 'assistant'

&#x20; content: string

&#x20; refs?: SourceItem\[]

&#x20; meta?: { messageId?: string; hitCount: number; elapsed: number; retrievalMs: number; llmMs: number }

&#x20; streaming?: boolean     // 正在生成（显示光标）

&#x20; stopped?: boolean       // 本地停止占位

&#x20; error?: string          // 错误消息（显示重试）

&#x20; createdAt: number

}
```

### 6.2 流状态机



```
idle ──send──▶ connecting ──meta──▶ streaming ──done──▶ idle（固化）

&#x20;                   │                    ├──error──▶ error ──重试/新问──▶ idle

&#x20;                   │                    ├──stop──▶ stopped ──▶ idle（占位）

&#x20;                   └──http/网络错──▶ error ──▶ idle

streaming 期间：输入禁用（B2）；controller 持有 abort 能力
```

### 6.3 事件 → 动作映射



| SSE 事件        | store action 逻辑                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `meta`        | 若 `is_new`：向 conversations 头部插入新会话；设置 `currentId`                                                                       |
| `references`  | 写入当前流式 assistant 消息的 `refs`                                                                                             |
| `delta`       | 追加 `content`（流式渲染）                                                                                                      |
| `done`        | 固化：`meta={messageId, hitCount, elapsed, retrievalMs, llmMs}`，`streaming=false`，state→idle；若 `hitCount===0` 消息带 "无命中" 样式 |
| `error`       | 若已出过 delta：在消息后追加错误尾巴；否则生成 ErrorBubble；state→error                                                                      |
| 客户端 abort（停止） | 消息置 `stopped=true` + 本地占位文本；state→stopped→idle                                                                          |
| 客户端超时 / 网络错   | state→error，`pendingQuestion` 保留供重试                                                                                     |

### 6.4 行为细则



* **发送**：`sendMessage(q)`：校验 streamState==='idle' → 先落本地 user 消息 + 空 assistant 消息 (streaming) → 新建 AbortController → `streamChat(...)`；

* **停止**（B1）：`controller.abort()` → 按映射处理。**副作用说明**：abort 时后端 user 消息已落库、assistant 未落库（未到 done），历史里该条 user 无对应回答 —— 前端以本地 "已停止" 占位展示，不写库；

* **重试**（B3）：`retryLast()`：取 `pendingQuestion` 重发（复用 sendMessage 路径），失败原因不重复累积；

* **会话操作**：切换会话 → 取消在途流（若有）→ `GET /{id}/messages` 拉历史（C1：refs 渲染折叠面板）；删除 → 确认弹窗 → DELETE + 本地移除；改名（C2）→ PATCH + 本地更新；

* **并发约束**：同一时刻仅一个会话一个流（B2 禁用输入 + 切换会话时 abort 兜底）；
* **模式切换**（方案 A）：`switchMode(mode)` → 取消在途流 → 置 `currentMode` → 清空消息区/currentId → 按新模式重拉会话列表；`sendMessage` 懒建会话与 `meta.is_new` 插入均带当前模式；`streamChat` 参数映射：`kb→dense`、`general→general`；`done.hit_count===0` 仅在 kb 模式显示 "无命中" 空态（general 的 hit\_count 恒 0，需按 currentMode 区分）。

| `PlaceholderView`     | 占位页  | 统一空态："该功能属于阶段 N，后端接口未上线"                                                                                         |

### 7.3 无命中 / 空态



* `done.hit_count===0`：消息正常展示（后端固定话术原样渲染），附带空态图标与 "可换个问法" 提示文案，不显示耗时行中生成耗时（llm\_ms=0）。

### 7.4 耗时行（E1）

assistant 消息底部次要文本：`检索 {retrieval_ms}ms · 生成 {llm_ms/1000}s · 总耗时 {elapsed}s`（无命中时省略生成段）。

**通用问答模式**（currentMode==='general'）：只显示 `生成 {llm_ms/1000}s`（无检索段、无总耗时；后端 retrieval\_ms=0）。

### 16.5 后续修复：重启弹出黑色控制台窗口（CREATE_NO_WINDOW）

**现象**：前端保存参数自动重启后，桌面多出一个标题为 `backend\.venv\Scripts\python.exe` 的黑色控制台窗口；用户关闭该窗口后新后端进程被杀，服务退出。

**根因**：`_schedule_restart` 的 `creationflags` 仅用了 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`。`DETACHED_PROCESS` 只保证新进程不继承父控制台，但 `python.exe` 作为控制台程序仍会**自建一个新的控制台窗口**——即用户看到的黑窗。关闭该窗口等同于终止新进程。

**进一步根因（venv launcher 二次 spawn）**：仅加 `CREATE_NO_WINDOW` 不够——venv 的 `python.exe` 是 launcher stub（约 241KB），Popen 后会二次 spawn 真正的基础 Python（`C:\Users\Admin\.workbuddy\binaries\python\versions\3.13.12\python.exe`），**二次 spawn 不继承父进程的 CREATE_NO_WINDOW**，因此黑色窗口仍会弹出。

**修复**（`config_service.py::_schedule_restart`）：
- Windows 下优先用同目录 `pythonw.exe`（无控制台版本）替换 `sys.executable`；venv 的 `pythonw.exe` launcher 二次 spawn 的目标也是 `pythonw.exe`，从根本上不创建控制台窗口；
- `creationflags` 追加 `CREATE_NO_WINDOW`（0x08000000）+ `STARTUPINFO`（`STARTF_USESHOWWINDOW | SW_HIDE`）双保险；
- 非 Windows 平台 `pythonw.exe` 不存在时回退 `sys.executable`，`CREATE_NO_WINDOW` 通过 `getattr` 安全降级为 0；
- 其余 spawn 逻辑（env 剔除可编辑参数、KB_WAIT_PORT=1、1.5s 延迟 os._exit）不变。

**验证**：干净启动 → API 保存 log_retention_days 30→31 → 新进程链 `venv\pythonw.exe → 基础 pythonw.exe`（均无控制台）→ 桌面截图确认**无任何黑色控制台窗口弹出** → 还原 30 → uptime 归零确认新进程接管；pytest 92 passed 无回归。

**Docker 环境**：Linux 容器无 Windows 控制台窗口概念，`subprocess.Popen` 不会弹出任何窗口，此问题天然不存在；`CREATE_NO_WINDOW` 在非 Windows 平台通过 `getattr(subprocess, "CREATE_NO_WINDOW", 0)` 安全降级为 0，不影响跨平台。
