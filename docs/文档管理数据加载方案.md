# 文档管理数据加载改造方案

> 状态：已确认待实施（2026-09-09）
> 背景：文档管理页已改为树状结构（folder 树 + 文件叶子，单表展示），
> 但数据加载仍沿用旧的分页接口"一次拉全量（page_size=20000）"，与树形交互不匹配。
> 本方案将加载方式改为"folder 树 + 按 folder 懒加载 + 搜索/筛选走后端"。

---

## 一、现状与问题

| 环节 | 现状 | 问题 |
|---|---|---|
| 数据加载 | `loadAllDocs()` 一次拉 `page_size=20000` 全量 | 文档多时首屏慢、内存大 |
| 树合并 | 前端 computed 对全量数组 filter/sort | 上万条每次渲染重算，卡顿 |
| 搜索/筛选 | 纯前端剪枝（displayTree） | 依赖全量数据，懒加载后此路不通 |
| 轮询 | 有非终态文档就每 3 秒全量拉 | 解析期间反复拉全量，浪费 |

**根本矛盾**：UI 已是"展开/折叠"的树形交互，数据层却仍是"一次全量搬回来"。

## 二、方案总览

**folder 树 + 按 folder 懒加载 + 搜索/筛选走后端**

1. 树骨架轻量加载：进页面只拉 folder 树（含递归计数），不拉文件
2. 展开 folder → 拉该 folder 直属文件（懒加载）；子 folder 展开时再加载
3. folder 行计数由 tree 接口递归 doc_count 提供，不依赖文件列表
4. 搜索/状态筛选走后端接口（跨树模糊搜索 + 状态过滤），结果按 folder 挂回树形展示
5. 轮询瘦身：仅在有"非终态文档"时轮询，且只刷新 folder 树计数 + 已展开 folder

## 三、前端数据模型改造（`frontend/src/stores/document.ts`）

```
当前：allDocs: DocumentItem[]            // 全量数组
改为：folderDocs: Map<string, DocumentItem[]>   // 按 folder_id 缓存已加载直属文件
      folderLoaded: Set<string>                 // 已加载标记（区分"加载过=空"与"未加载"）
      loadingFolderIds: Set<string>             // 展开加载中的 folder（UI 显示"加载中"）
      searchResults: DocumentItem[] | null      // 搜索/筛选结果集（null = 非搜索态）
```

- `mixedTree` 构建：folder 行的子 folder 来自 `folderTree`；直属文件来自 `folderDocs.get(folder_id)`（未加载为空数组）；搜索态下文件改用 `searchResults` 按 `folder_id` 过滤
- 兼容保留 `allDocs` 计算属性（对外引用不受影响）

## 四、加载流程

| 动作 | 行为 |
|---|---|
| 进页面 | `loadKbs()` + `loadFolderTree()`，不拉文件；默认展开顶层 folder 并触发其加载 |
| 展开 folder | 无缓存 → `GET /api/documents?kb_id&folder_id=X&page_size=5000` 拉直属文件 → 写 `folderDocs`；有缓存直接展示；加载中 folder 行显示"加载中…" |
| 搜索 / 状态筛选 | `GET /api/documents?kb_id&search=&status=&page_size=5000`（后端已支持）→ 命中结果挂回对应 folder 节点；folder 行计数显示"命中 N"；清空后恢复缓存视图 |
| 轮询 | 每 3 秒调 `GET /api/documents/summary?kb_id=` → `in_progress=0` 即停；否则刷新 folder 树计数 + 覆盖式重拉已展开 folder（更新状态 tag） |

## 五、后端改动（最小）

**新增 1 个轻量接口**（其余全部复用现有接口）：

```
GET /api/documents/summary?kb_id=default
→ { total, pending, ingesting, embedding, done, failed, in_progress }
```

- 实现：`queries.count_documents_by_status`（单条 `GROUP BY status` 查询）→ `document_service.count_documents_by_status` → 路由挂在 `/summary`（**必须定义在 `/{doc_id}` 系列路由之前**，避免被捕获）
- 用途：轮询判断"是否存在非终态文档"，避免轮询拉全量

## 六、缓存失效规则（重点）

**任何变更操作完成后统一执行**：刷新 `loadFolderTree` + `loadKbs`（计数），并清空相关 folder 缓存：

| 操作 | 失效范围 |
|---|---|
| 上传文件 | 目标 folder 缓存失效 |
| 删除文档 | 所在 folder 缓存失效 |
| 移动文件 | **源 folder + 目标 folder** 都失效（覆盖场景：先展开 A → 移文件进 A → 再展开 A 重新拉取、看到新文件） |
| 重命名 / 移动 folder | 该 folder 子树下所有 folder 缓存失效（folder_path 变化，缓存路径提示过期） |
| 删除 folder | 子树内所有 folder 缓存删除 |
| 重解析 | 所在 folder 缓存失效 |

> 失效 = 从 `folderDocs` 删除条目 + `folderLoaded` 移除标记，下次展开自动重拉，不额外请求。

## 七、边界处理

- **展开加载中**：`loadingFolderIds` 标记，folder 行名称旁显示"加载中…"；数据到达后自动渲染
- **空 folder**：`folderLoaded` 区分"加载过为空"与"未加载"，避免空 folder 每次展开重复请求
- **选中与上传目标**：`selectNode` 的 folder 推断改从 `folderDocs` / `searchResults` 查找
- **搜索与筛选组合**：search + status 可同时传参（后端已支持）
- **切换知识库**：清空 `folderDocs` / `folderLoaded` / `expandedKeys`，重新加载新 kb 的树

## 九、验证

1. 后端：`python -m app.run` 启动后 `GET /api/documents/summary?kb_id=default` 返回各状态计数
2. 前端：`npm run test`（document store 单测）+ 浏览器验证：
   - 进页面只请求 folder 树（无全量 documents 请求）
   - 展开 folder 才请求该 folder 文件；再折叠/展开不重复请求
   - 搜索/状态筛选走 `/documents?search=&status=`，清空恢复缓存视图
   - 移动文件到已展开 folder 后，再展开能看到新文件（缓存失效生效）
   - 上传后轮询仅请求 summary + 已展开 folder，无全量请求
